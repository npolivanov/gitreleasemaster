## Диагноз: «конфликт не показывается, ничего не происходит, коммита нет в ветке»

Симптом означает: репозиторий, скорее всего, **остался в незавершённом cherry-pick состоянии** (конфликт случился, коммит не создан — поэтому `git log --grep` не находит), а ответ хоста до webview не дошёл или не был отправлен. Три причины по убыванию вероятности:

1. **VS Code работает старой сборкой расширения.** Если после последней компиляции не сделан Reload Window — запущенный extension host не имеет обработчика `cherryPick` (или старую версию) → сообщение обрабатывается вхолостую, ответ не приходит никогда → вечный loader «как будто ничего не происходит». Проверка: в `Output → Extension Host` при нажатии «Применить» должна появляться строка `[Git Release Master] cherryPick …`. Нет строки → старая сборка.
2. **Детект конфликта недостаточно надёжен.** Сейчас конфликт определяется только через `status().conflicted` (парсер simple-git). Если он вернул пустой массив (особенность парсинга/версии), конфликтный cherry-pick уйдёт в ветку `error`/`skip` без конфликтного UI, а репозиторий останется в состоянии конфликта.
3. **Нет safety net в handler'ах.** Любое непойманное исключение в `handleCherryPick` → ответ не отправляется вообще → вечный loader (расширение молчит).

## Фикс

### 1. `src/git.ts` — пуленепробиваемый детект конфликта
В `cherryPickCommit` (и `cherryPickContinue`) после падения cherry-pick:
- конфликтные файлы: `status().conflicted`, а при пустоте — fallback `git diff --name-only --diff-filter=U` (raw);
- конфликт считается обнаруженным, если **файлы есть** ИЛИ существует `CHERRY_PICK_HEAD` (`git rev-parse -q --verify CHERRY_PICK_HEAD` exit 0 — признак незавершённого cherry-pick);
- в catch: если сообщение матчит `/already in progress/` (sequencer от прошлого конфликта) — тоже возвращать `conflict` с текущими файлами, а не безликий error.

### 2. Handler'ы — гарантированный ответ + диагностика
`handleCherryPick.ts`, `handleCherryPickContinue.ts`, `handleCherryPickAbort.ts`:
- обернуть тело в try/catch — при любом исключении отправлять результат со `status: "error"` и текстом исключения. Вечный loader становится невозможным: webview всегда получает ответ;
- расширить `console.log`: команда принята → итог (статус, ветка, количество конфликтных файлов, наличие CHERRY_PICK_HEAD). Всё видно в `Output → Extension Host`.

### 3. UI — мелкое улучшение наблюдаемости
`commits-preview.tsx`: в текст конфликтного Alert'а добавить shortSha конфликтного коммита («Конфликт при применении `2990e0b`…»).

### 4. Синтетический тест конфликта (перед сборкой)
Скрипт в /tmp-репо: base-коммит → feature-ветка с изменением файла → release-ветка без него → выполнить точную последовательность вызовов `cherryPickCommit` (cherry-pick → catch → status().conflicted → CHERRY_PICK_HEAD) и распечатать, что возвращает каждый детектор. Это подтвердит/опровергнет гипотезу №2 и проверит фикс на реальном конфликте, плюс сценарий `--continue` после ручного резолва.

### 5. Сборка
`npm run compile` + `npm run build-webview`. Напомнить: **Reload Window обязателен**.

## Как проверить после фикса
1. Reload Window.
2. Output → Extension Host: при «Применить» обязана появиться строка `cherryPick … на «release/…»: conflict` (или applied/skipped). Нет строки — расширение не перезагрузилось.
3. При конфликте: alert с файлами + кнопки; резолв в Source Control → «Продолжить» → коммит появляется в ветке (`git log <release> --grep`).
