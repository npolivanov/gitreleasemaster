## План: Режим удаления коммитов из релизной ветки (git revert)

### Суть
При активном чекбоксе «Режим удаление»:
- `resolveCommits` проверяет вхождение коммитов **в релизную ветку** (`releaseCtx.branch`), а не в upstream — удаляем из релиза;
- резолвнутые коммиты показываются во **второй панели** «Коммиты для удаления» (на месте закомментированного `CommitsPreview` в `commits.tsx`), сортировка **от новых к старым** (обратная добавлению — корректный порядок revert);
- кнопка «Применить» по очереди выполняет `git revert <sha>`; конфликты — тот же UX, что у cherry-pick (alert + Открыть конфликты + Заново + Прервать).

### Шаг 1. Host: `revertCommit` в `src/git.ts`
Зеркало `cherryPickCommit`, отличия:
- команда `git revert --no-edit <sha>` (`--no-edit` — валидный флаг, не запрещённый core.editor);
- pending-детект через **`REVERT_HEAD`** (не CHERRY_PICK_HEAD);
- доводка: `git revert --continue`; пустой патч: `git revert --skip`;
- результат — переиспользуем `CherryPickResult` (статусы applied/skipped/conflict/error + files + branch подходят revert'у один в один).
Заодно: переименовать параметр `upstreamBranch` → `branch` в `resolveCommits` (ветка теперь может быть и релизной — имя не должно врать).

### Шаг 2. Host: обёртки и протокол
- `src/host/branches.ts`: +`safeRevert(sha, branch?)`; переименовать параметр `safeResolveCommits`.
- `src/host/messages.ts`: 
  - `resolveCommits` data: `{ upstreamBranch }` → `{ branch }`;
  - +`{ command: "revert"; data: { sha: string; branch?: string } }` (in);
  - +`{ command: "revertResult"; data: CherryPickResult }` (out).
- **Новый** `src/host/commands/handleRevert.ts` (зеркало handleCherryPick: try/catch + логи).
- `handleResolveCommits.ts`: `message.data.branch`.
- `src/host/messageRouter.ts`: +case `"revert"`.
- Abort: `cherryPickAbort` (`git cherry-pick --abort`) — git-sequencer общий для cherry-pick/revert («no cherry-pick or revert in progress» в сообщениях об ошибке это подтверждает); кросс-совместимость проверю синтетическим тестом, при проблеме добавлю `revertAbort`.

### Шаг 3. Webview: типы
`webview-ui/src/types.ts`: mirror — rename `upstreamBranch`→`branch` в resolveCommits, +`revert`/`revertResult`.

### Шаг 4. Webview: хук с режимом
`use-apply-commits.ts`: signature `useApplyCommits(commits, branch?, mode: "pick" | "revert" = "pick")`:
- команда: `cherryPick` | `revert`; событие: `cherryPickResult` | `revertResult` (по modeRef, как branchRef);
- вся стейт-машина (очередь, conflict-стоп, restart-со-следующего, abort) — без изменений, она режимо-независима.

### Шаг 5. Webview: `commits.tsx` — два режима
- `onSubmit`: без early-return; целевая ветка резолва: `isDeleteMode ? releaseCtx?.branch : data.upstreamBranch` (+ валидация непустой ветки в обоих режимах).
- `sortedCommits`: направление по режиму — добавление: старые→новые (asc); удаление: новые→старые (desc).
- Правая часть: `{!isDeleteMode && <CommitsPreview title="Коммиты для добавления" mode-по-умолчанию/>}` + разкомментировать второй блок как `{isDeleteMode && <CommitsPreview title="Коммиты для удаления" branch={releaseCtx?.branch} mode="revert"/>}`.
- `CommitsPreview` += пропс `mode?: "pick" | "revert"` (пробрасывается в хук). UI компонента не меняется (переиспользование, как просили).

### Шаг 6. Синтетическая проверка (/tmp-репо)
1. `revert --no-edit` чистый → applied.
2. Revert-конфликт → unmerged-файлы + REVERT_HEAD → conflict.
3. Stage-резолв → повторный вызов revertCommit → авто-`revert --continue` → applied.
4. `git cherry-pick --abort` при активном revert-конфликте → работает (или фикс через revertAbort).
5. Повторный revert того же sha → skipped(empty-patch).

### Шаг 7. Сборка
`npm run compile` + `npm run build-webview` + напоминание Reload Window.
